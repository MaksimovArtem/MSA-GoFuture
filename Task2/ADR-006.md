# ADR-006: Архитектура событийной платформы GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture должна поддерживать обработку более 500000 конкурентных поездок, динамическое ценообразование в real-time и умное распределение водителей. Эти требования уже зафиксированы в ADR-001 как ключевые функциональные и нефункциональные требования

Текущая система использует Django-монолит, общую PostgreSQL БД, REST API и AMQP/RabbitMQ для асинхронных задач
Для целевой микросервисной архитектуры требуется событийная платформа, которая позволит сервисам обмениваться доменными событиями, масштабировать обработку по регионам и строить real-time сценарии

## 2. Требования

Событийная платформа должна обеспечивать:

- публикацию и обработку доменных событий
- масштабирование обработки по регионам
- поддержку real-time сценариев: динамическое ценообразование, обновление статусов водителей, антифрод и аналитика
- надежную доставку событий
- возможность восстановления после ошибок обработки
- мониторинг Kafka, потребителей, lag, ошибок и бизнес-метрик
- интеграцию с To-Be архитектурой GoFuture

### 3.1 Технология

В качестве основной событийной платформы выбирается Apache Kafka

Kafka используется для:

- обмена доменными событиями между микросервисами
- потоковой обработки событий
- расчета агрегатов для Pricing, Driver Matching, Fraud и Analytics
- интеграции runtime-сервисов с аналитическим хранилищем

RabbitMQ может временно сохраняться на переходном этапе для старых задач, но новые доменные события публикуются в Kafka

### 3.2 Модель доменных событий

| Событие               | Домен        | Сервисы-генераторы        | Сервисы-получатели                         |
| --------------------- | ------------ | ------------------------- | ------------------------------------------ |
| BookingCreated        | Booking      | Booking                   | Pricing, Driver, Fraud, Analytics          |
| BookingCancelled      | Booking      | Booking                   | Driver, Payments, Notification, Analytics  |
| BookingConfirmed      | Booking      | Booking                   | Notification, Analytics                    |
| DriverLocationUpdated | Driver       | Driver                    | Pricing, Driver, Analytics                 |
| DriverMatched         | Driver       | Driver                    | Booking, Notification, Fraud, Analytics    |
| PriceCalculated       | Pricing      | Pricing                   | Booking, Payments, Analytics               |
| PaymentAuthorized     | Payments     | Payments                  | Booking, Notification, Fraud, Analytics    |
| PaymentFailed         | Payments     | Payments                  | Booking, Notification, Fraud, Analytics    |
| NotificationRequired  | Notification | Booking, Payments, Driver | Notification                               |
| NotificationSent      | Notification | Notification              | Analytics                                  |
| FraudCheckPassed      | Fraud        | Fraud                     | Booking, Payments, Analytics               |
| FraudCheckFailed      | Fraud        | Fraud                     | Booking, Payments, Notification, Analytics |

### 3.3 Схема топиков Kafka

Топики разделяются по доменам. Партиционирование выполняется с учетом региона, чтобы события одного региона можно было обрабатывать независимо и масштабировать отдельно

| Топик               | События                                            | Ключ партиционирования        | Основные потребители                                      |
| ------------------- | -------------------------------------------------- | ----------------------------- | --------------------------------------------------------- |
| booking.events      | BookingCreated, BookingCancelled, BookingConfirmed | region_id + booking_id        | Driver, Pricing, Payments, Notification, Fraud, Analytics |
| driver.events       | DriverMatched                                      | region_id + driver_id         | Booking, Pricing, Fraud, Analytics                        |
| driver.location     | DriverLocationUpdated                              | region_id + driver_id         | Driver Matching, Pricing, Analytics                       |
| pricing.events      | PriceCalculated                                    | region_id + pricing_id        | Booking, Payments, Analytics                              |
| payments.events     | PaymentAuthorized, PaymentFailed                   | region_id + payment_id        | Booking, Notification, Fraud, Analytics                   |
| notification.events | NotificationRequired, NotificationSent             | region_id + notification_id   | Notification, Analytics                                   |
| fraud.events        | FraudCheckPassed, FraudCheckFailed                 | region_id + check_id          | Booking, Payments, Notification, Analytics                |
| dead-letter.events  | События, которые не удалось обработать             | region_id + original_event_id | Support / SRE / сервис-владелец                           |

Для высокочастотных событий, например `DriverLocationUpdated`, используется отдельный топик `driver.location`, чтобы не смешивать частые технические обновления с бизнес-событиями жизненного цикла поездки.

### 3.4 Потоковая обработка событий

Для обработки событий в реальном времени используются потоковые обработчики на базе Apache Flink

Flink выбирается как основной инструмент, так как он подходит для обработки больших потоков событий, расчета агрегатов по временным окнам и построения real-time сценариев. Kafka используется как транспорт событий, а Flink читает события из Kafka, обрабатывает их и публикует результаты обратно в Kafka или записывает в аналитическое хранилище

| Обработчик                 | Входные события                                      | Результат                                                           |
| -------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------- |
| Pricing Stream Processor   | BookingCreated, DriverLocationUpdated, DriverMatched | Расчет спроса, предложения и динамических коэффициентов по регионам |
| Driver Matching Processor  | BookingCreated, DriverLocationUpdated                | Подготовка данных для подбора водителя и предотвращения горячих зон |
| Fraud Stream Processor     | BookingCreated, PaymentAuthorized, PaymentFailed     | Выявление подозрительных поездок и платежных операций               |
| Analytics Stream Processor | События доменов Booking, Driver, Pricing, Payments и Fraud | Подготовка real-time аналитики и запись агрегатов в ClickHouse      |

Обработка событий выполняется с учетом регионального партиционирования Kafka. Это позволяет независимо масштабировать обработку событий в разных регионах и снижает риск влияния нагрузки одного региона на остальные.

Таким образом:

- Kafka отвечает за хранение и доставку событий
- Flink отвечает за потоковую обработку и real-time агрегаты
- доменные сервисы используют результаты обработки для ценообразования, подбора водителей, антифрода и аналитики

### 3.5 Saga

Для жизненного цикла поездки выбирается оркестрируемая Saga

Причина: сценарий заказа поездки затрагивает несколько критичных сервисов — Booking, Pricing, Driver, Payments, Notification и Fraud. Центральная координация упрощает контроль статусов и обработку ошибок

Координатор Saga: Booking Service

#### Основной сценарий (happy path)

В таблице ниже используются как доменные события, так и команды, инициирующие действия в других сервисах.

| Шаг | Команда / событие    | Участник                |
| --- | -------------------- | ----------------------- |
| 1   | BookingCreated       | Booking                 |
| 2   | PriceRequested       | Booking -> Pricing      |
| 3   | PriceCalculated      | Pricing                 |
| 4   | FraudCheckRequested  | Booking -> Fraud        |
| 5   | FraudCheckPassed     | Fraud                   |
| 6   | DriverMatchRequired  | Booking -> Driver       |
| 7   | DriverMatched        | Driver                  |
| 8   | PaymentRequested     | Booking -> Payments     |
| 9   | PaymentAuthorized    | Payments                |
| 10  | BookingConfirmed     | Booking                 |
| 11  | NotificationRequired | Booking -> Notification |

Notification не входит в критичный путь успешного создания поездки. Если push-уведомление не отправилось, поездка не должна отменяться

#### Компенсирующие события

| Ошибка                          | Компенсация                                                  |
| ------------------------------- | ------------------------------------------------------------ |
| Pricing не смог рассчитать цену | BookingFailed                                                |
| Fraud отклонил поездку          | BookingCancelled                                             |
| Driver не найден                | BookingCancelled                                             |
| Payment не прошел               | BookingCancelled, PaymentFailed                              |
| Notification не отправлен       | Поездка не отменяется, событие уходит на повторную обработку |

### 3.6 Надежная доставка событий

Используются следующие механизмы:

| Механизм                         | Описание                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Transactional Outbox             | Сервис сохраняет бизнес-изменение и событие в outbox-таблицу в одной транзакции своей БД. Outbox Publisher публикует эти события в Kafka |
| Идемпотентные producer/consumer  | Повторная отправка или повторная обработка события не должна создавать дубли поездок, платежей и статусов                       |
| Consumer offsets после обработки | Offset фиксируется только после успешной обработки события                                                                      |
| Retry topics                     | Временные ошибки обрабатываются через повторные попытки                                                                         |
| Dead Letter Topic                | События, которые не удалось обработать после нескольких попыток, отправляются в `dead-letter.events`                            |
| Correlation ID                   | Все события одного бизнес-сценария содержат общий `correlation_id`                                                              |

Для критичных операций, например доменов Booking и Payments, обработчики должны быть идемпотентными

### 3.7 Мониторинг и метрики

Используются следующие инструменты:

| Инструмент     | Назначение                                  |
| -------------- | ------------------------------------------- |
| Prometheus     | Сбор технических и бизнес-метрик            |
| Grafana        | Дашборды Kafka, сервисов и бизнес-сценариев |
| Loki           | Централизованные логи                       |
| Alertmanager   | Алерты по техническим и бизнес-метрикам     |
| OpenTelemetry  | Трейсинг запросов и событий между сервисами |


Эти инструменты согласуются с текущим стеком GoFuture

#### Основные технические метрики

Для событийной платформы отслеживаются следующие метрики:

| Компонент         | Метрики                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| Kafka Broker      | доступность брокеров, количество недоступных партиций, количество партиций без нужного числа реплик |
| Kafka Consumer    | consumer lag, скорость чтения сообщений, количество ошибок обработки                                |
| Kafka Producer    | скорость публикации событий, количество ошибок публикации                                           |
| Dead Letter Queue | количество событий, попавших в DLQ, типы ошибочных событий                                          |
| Flink             | статус jobs, скорость обработки событий, задержка обработки, количество ошибок                      |

Основные алерты:

- недоступен Kafka broker
- появились offline partitions
- растет consumer lag
- события попадают в DLQ
- остановился Flink job
- растет задержка обработки событий
- появились ошибки публикации или чтения событий

#### Основные бизнес-метрики

| Сценарий        | Метрики |
| --------------- | ------- |
| Booking         | количество созданных поездок, отмены, ошибки создания |
| Driver Matching | время подбора водителя, доля ненайденных водителей |
| Pricing         | время расчета цены, количество ошибок расчета, изменение surge-коэффициента |
| Payments        | успешные оплаты, неуспешные оплаты, повторные попытки, ошибки выплат |
| Fraud           | количество отклоненных операций, количество подозрительных поездок |
| Notification    | успешные и неуспешные отправки push-уведомлений |
| Analytics       | задержка доставки событий в аналитическое хранилище |

### 3.8 Интеграция в To-Be архитектуру

В To-Be архитектуру добавляются следующие контейнеры:

- Kafka Cluster
- Outbox Publisher
- Flink Cluster

Основные связи:

- доменные сервисы публикуют события в Kafka
- доменные сервисы потребляют события из Kafka
- Flink обрабатывает потоки событий для Pricing, Driver Matching, Fraud и Analytics
- Analytics Service записывает агрегированные данные в ClickHouse
- Prometheus собирает метрики Kafka, сервисов и Flink
- Grafana отображает технические и бизнес-дашборды
- Alertmanager отправляет алерты при росте lag, ошибок, DLQ и деградации бизнес-сценариев

## 4. Последствия

### Положительные

- Сервисы могут обмениваться событиями без жесткой синхронной связанности
- Поддерживается real-time обработка для Pricing, Driver Matching, Fraud и Analytics
- События можно масштабировать по регионам через партиционирование
- Упрощается построение аналитики и ML-пайплайнов
- Повышается устойчивость системы к временным сбоям отдельных сервисов

### Отрицательные

- Появляется дополнительная инфраструктурная сложность
- Возрастает сложность отладки распределенных сценариев
- Нужно следить за consumer lag, DLQ и ошибками stream-processing
- Разработчикам нужно соблюдать правила идемпотентной обработки событий
