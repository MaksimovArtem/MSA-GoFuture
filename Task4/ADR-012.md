# ADR-012: Data Platform для аналитики, BI и ML-моделей GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture требуется единая платформа сбора, обработки и анализа данных для динамического ценообразования, прогнозирования спроса, антифрода и BI
В целевой архитектуре GoFuture уже используются доменные микросервисы, Kafka для доменных событий, Flink для потоковой обработки и ClickHouse как аналитическое хранилище
Необходимо связать данные из микросервисов с ML-платформой и BI-инструментами

## 2. Требования

Data Platform должна обеспечивать:

- сбор данных из всех доменных микросервисов
- обработку событий в near real-time
- подготовку данных для ML-моделей
- передачу агрегированных данных в BI-инструменты
- контроль качества данных
- соблюдение ограничений по персональным и платежным данным
- возможность использовать данные для Driver, Pricing и Fraud сервисов

## 3. Решение

Для GoFuture выбирается событийная data platform

Основной поток данных:

1. Доменные сервисы публикуют события в Kafka
2. Flink читает события из Kafka и выполняет потоковую обработку
3. Data Quality слой проверяет корректность, полноту и свежесть данных
4. Очищенные и агрегированные данные записываются в ClickHouse
5. ML Platform использует подготовленные признаки и обучает модели
6. BI-инструмент DataLens использует ClickHouse для отчетности и дашбордов
7. Модели возвращают результаты в доменные сервисы: Driver, Pricing и Fraud

## 4. Основные потоки данных

| Источник             | Данные                                                     | Использование                                                        |
| -------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| Booking Service      | создание заказа, отмена, подтверждение, завершение поездки | спрос, конверсия, история поездок, обучение моделей                  |
| Driver Service       | статусы водителей, геопозиция, назначение водителя         | прогноз доступности, driver matching, горячие зоны                   |
| Pricing Service      | рассчитанные цены, коэффициенты, ошибки расчета            | анализ ценообразования, обучение pricing-модели                      |
| Payments Service     | успешные и неуспешные оплаты, выплаты                      | финансовая аналитика, fraud detection                                |
| Geography Service    | регионы, зоны, маршруты                                    | геоаналитика, региональные признаки для ML                           |
| Fraud Service        | результаты проверок, подозрительные операции               | обучение антифрод-моделей                                            |

## 5. Использование данных

| Сценарий                     | Какие данные используются           | Результат                                           |
| ---------------------------- | ----------------------------------- | --------------------------------------------------- |
| Динамическое ценообразование | Booking, Driver, Geography, Pricing | расчет спроса, предложения и коэффициентов          |
| Прогнозирование спроса       | Booking, Driver, Geography          | прогноз горячих зон и будущего спроса               |
| Обнаружение мошенничества    | Booking, Payments, Driver, Fraud    | fraud score и правила блокировки                    |
| BI и отчетность              | агрегированные события всех доменов | дашборды по поездкам, оплатам, водителям и регионам |

## 6. Механизмы качества данных

Для обеспечения качества данных используются следующие механизмы

| Механизм                 | Описание                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------- |
| Валидация схемы события  | Проверяется, что событие содержит обязательные поля                                     |
| Проверка дубликатов      | Повторные события определяются по event_id и не должны повторно влиять на агрегаты      |
| Проверка свежести данных | Контролируется задержка между временем события и временем попадания в аналитику         |
| Проверка полноты потока  | Контролируется, что по ключевым доменам не пропал поток событий                         |

## 7. Последствия

### Положительные

- Появляется единый поток данных из микросервисов в аналитику и ML
- ML-модели получают данные из доменных событий, а не из прямых запросов в базы сервисов
- BI-инструменты работают с подготовленными витринами в ClickHouse
- Данные для сервисов Driver, Pricing и Fraud обрабатываются near real-time
- Появляется контроль качества данных на ключевых этапах пайплайна

### Отрицательные

- Появляется дополнительная инфраструктурная сложность
- Требуется сопровождать правила качества данных
- Ошибки в событиях могут влиять на аналитику и ML-модели
- Не все данные можно использовать в глобальной аналитике из-за compliance-ограничений
