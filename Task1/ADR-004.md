# ADR-004: Механизмы обеспечения обратной совместимости при миграции GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture переходит от Django-монолита к микросервисной архитектуре. 
Текущая система использует REST API для синхронного взаимодействия и AMQP/RabbitMQ для асинхронных задач. Клиентские приложения уже существуют: iOS, Android, Huawei Mobile Services, корпоративный портал и админ-панель.
## 2. Требования

Необходимо сохранить работоспособность на период миграции для:
- существующих мобильных приложений
- корпоративного портала
- внешних API

Обратная совместимость уже зафиксирована(требование +R2) как ограничение в ADR-001: на период миграции должна сохраняться совместимость с существующими мобильными приложениями и API

## 3. Решение

Для обеспечения обратной совместимости на уровне API будут применяться:

| Механизм                             | Описание                                                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API Gateway/Compatibility Layer      | Внешние клиенты продолжают работать через существующие API-контракты. API Gateway маршрутизирует запросы либо в монолит, либо в новый микросервис.        |
| Версионирование API                  | Существующие контракты сохраняются как `v1`. Новые или измененные контракты публикуются как `v2`. Поддерживаются обе версии                               |
| Поддержка обратной совместимости API | Новые поля добавляются как optional, старые поля не удаляются без периода поддержки                                                                       |
| Политика обратной совместимости      | Устаревшие версии API обрабатываются в соответствии с политикой обратной совместимости компании. Например, удаляются после завершения переходного периода |
| Контрактное тестирование             | Для ключевых API проверяется, что изменения не ломают существующих клиентов                                                                               |

Для обеспечения обратной совместимости внутри продукта будут применяться:

| Механизм                                      | Описание                                                                                                                                                               |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Маршрутизация согласно паттерну Strangler Fig | Трафик переключается на вынесенный сервис постепенно. Во время миграции часть функционала остается в монолите                                                          |
| Адаптеры к монолиту                           | На переходном этапе новые сервисы могут использовать адаптеры для взаимодействия с монолитом и его данными                                                             |
| Выборочное применение новых фич               | Новая реализация включается постепенно: по региону, пользователю, проценту трафика или типу клиента<br>Например, сначала у клиентов, согласившихся на тестирование фич |
| Версионирование событий                       | События между сервисами версионируются. Потребители должны корректно обрабатывать неизвестные optional-поля.                                                           |

Также необходимо поддержать идемпотентность операций в момент миграции, чтобы запросы к монолиту и выделенным сервисам не дублировали операции заказа/оплаты 

## 4. Альтернативы

### 4.1 Переход на новый API без версионирования

Не выбрано, так как приведет к поломке существующих приложений и партнерских интеграций

### 4.2 Оставить только монолитные API до конца миграции

Не выбрано, так как это замедлит переход к независимым сервисам и сохранит сильную связанность с монолитом
## 5. Последствия

### Положительные

- Существующие мобильные приложения и API продолжают работать во время миграции
- Снижается риск поломки критичных пользовательских сценариев
- Новые сервисы можно включать постепенно
- Появляется контроль над изменениями API и событий

### Отрицательные

- На переходном этапе появляется дополнительный слой совместимости
- Придется поддерживать несколько версий API
- Возрастает сложность тестирования контрактов(старых для обратной совместимости и новых)
- Возможна временная дубликация логики между монолитом и новыми сервисами
- Требуется дисциплина и контроль над изменениями API и событий
