# ADR-010: Аварийное переключение между регионами GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture разворачивается в нескольких географических регионах для обеспечения низкой задержки и высокой доступности

В ADR-007 выбраны регионы развертывания:

- Singapore
- Jakarta
- Malaysia
- São Paulo
- Santiago

В ADR-008 выбрана модель regional ownership: каждый пользователь, водитель, поездка и платеж имеют основной регион хранения, а критичные данные асинхронно реплицируются в резервный регион

Для выполнения требования по доступности 99,95% необходимо определить механизм аварийного переключения при отказе региона или отдельных критичных компонентов

## 2. Требования

Механизм failover должен обеспечивать:

- автоматическое или полуавтоматическое переключение трафика при отказе региона
- исключение недоступного региона из маршрутизации
- сохранение работоспособности критичных сценариев
- минимизацию потери данных
- защиту от дублирования платежей и поездок
- возможность восстановления основного региона после инцидента
- понятную схему диагностики и мониторинга

## 3. Решение

Для аварийного переключения используется связка:

- Global Traffic Manager / GeoDNS
- Regional Health Checks
- региональные API Gateway
- резервные регионы
- асинхронная репликация критичных данных
- Kafka DLQ и retry-механизмы
- observability stack: Prometheus, Grafana, Loki, Alertmanager, OpenTelemetry

C4-диаграмма аварийного переключения на примере Южной Америки представлена в **Failover_C4.png**.

Основной принцип:

- пользовательский трафик идет через Global Traffic Manager
- Global Traffic Manager проверяет состояние регионов через health checks
- если регион недоступен, он исключается из маршрутизации
- трафик направляется в резервный регион
- резервный регион временно принимает нагрузку и становится владельцем новых операций
- после восстановления основного региона выполняется сверка данных и обратная синхронизация

## 4. Основные точки отказа

| Точка отказа | Что ломается | Механизм обнаружения | Механизм переключения |
|---|---|---|---|
| Региональный API Gateway | Пользователи не могут попасть в регион | Health checks, рост 5xx, timeout | Global Traffic Manager исключает регион из маршрутизации |
| Доменные сервисы региона | Нарушаются сценарии заказа, оплаты, подбора водителя | Метрики сервисов, error rate, latency, алерты | Трафик ограничивается или переводится в резервный регион |
| Региональная БД | Сервисы не могут читать или писать данные | DB health checks, ошибки подключения, рост latency | Используется реплика в резервном регионе |
| Kafka Cluster региона | Нарушается публикация и обработка событий | Kafka metrics, consumer lag, offline partitions | Новые события пишутся в Kafka резервного региона после failover |

## 5. Таблица сценариев отказа

| Сценарий отказа | Пример | Действие системы | Результат |
|---|---|---|---|
| Отказ одной availability zone | Недоступна часть инфраструктуры внутри региона | Регион продолжает работать через другие зоны доступности | Пользовательский трафик остается в том же регионе |
| Отказ регионального API Gateway | São Paulo API Gateway не отвечает | Health checks помечают регион как недоступный | Traffic Manager переводит трафик на Santiago |
| Отказ критичного сервиса | Payments Service в São Paulo недоступен | Срабатывают алерты, включаются retry и circuit breaker | Платежный сценарий деградирует или трафик переводится в резервный регион |
| Отказ региональной БД | Service DB в São Paulo недоступна | Запись в основном регионе останавливается | Santiago временно становится регионом записи |
| Отказ Kafka в регионе | Kafka São Paulo недоступна | Публикация событий в регионе останавливается или уходит в retry | После failover события публикуются в Kafka резервного региона |
| Полный отказ São Paulo | Основной регион Южной Америки недоступен | Health checks исключают регион из маршрутизации | Трафик Южной Америки переключается в Santiago |
| Восстановление São Paulo | Основной регион снова доступен | Выполняется сверка данных и событий | Трафик постепенно возвращается в São Paulo |

## 6. Особенности переключения

При аварийном переключении важно соблюдать следующие правила:

- активные поездки не должны терять состояние
- платежные операции не должны дублироваться
- после восстановления региона выполняется сверка данных и событий
- возврат трафика в основной регион выполняется постепенно

## 7. Последствия

### Положительные

- Отказ одного региона не приводит к полной остановке платформы
- Пользователи могут быть автоматически переведены в резервный регион
- Механизм failover согласован с regional ownership и репликацией
- Снижается MTTR при региональных инцидентах

### Отрицательные

- Усложняется эксплуатация инфраструктуры
- Появляется необходимость регулярно проверять failover
- Возможна задержка данных из-за асинхронной репликации
- Требуется сверка данных после восстановления региона
- Multi-cloud failover São Paulo -> Santiago усложняет эксплуатацию
