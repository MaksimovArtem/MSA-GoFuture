# ADR-011: Стратегия комплаенса GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture разворачивается в нескольких географических регионах: Singapore, Jakarta, Malaysia, São Paulo и Santiago

Платформа работает с персональными данными пассажиров и водителей, данными поездок, платежными операциями, корпоративными клиентами и локальными интеграциями. Поэтому архитектура должна учитывать локальные регуляторные требования разных стран и регионов

## 2. Требования

Стратегия комплаенса должна обеспечивать:

- хранение и обработку данных с учетом региона пользователя
- ограничение межрегиональной передачи персональных и платежных данных
- возможность локального хранения данных там, где это требуется
- контроль доступа к данным по ролям и регионам
- аудит действий пользователей, администраторов и сервисов
- безопасную работу с платежными и банковскими интеграциями
- возможность удаления, анонимизации или ограничения обработки данных

## 3. Решение

Для GoFuture выбирается стратегия regional data compliance

Основной принцип: данные пользователя, водителя, поездки и платежа должны храниться и обрабатываться в регионе, к которому они относятся, если локальные требования не разрешают иное

Это согласуется с моделью regional ownership: каждый объект имеет основной регион хранения, а межрегиональная репликация выполняется только там, где это допустимо и необходимо

## 4. Классификация данных

|Тип данных|Примеры|Подход|
|---|---|---|
|Персональные данные|имя, телефон, email, идентификаторы пользователя|Хранить в регионе пользователя или разрешенном регионе обработки|
|Данные водителей|профиль, документы, статус, регион работы|Хранить в регионе работы водителя|
|Данные поездок|заказ, маршрут, статусы, история поездки|Хранить в регионе создания поездки|
|Платежные данные|статус оплаты, внешний payment id, данные выплат|Хранить в регионе операции или в регионе платежного провайдера|
|Геоданные|координаты, маршруты, зоны|Обрабатывать локально; историю хранить только при необходимости|
|Аналитические данные|агрегаты, метрики, отчеты|Передавать между регионами в агрегированном или обезличенном виде|
|Технические данные|логи, трейсы, метрики|Не включать чувствительные данные без необходимости|

## 5. Контроль доступа

Доступ к данным строится по принципам:

- минимально необходимых прав
- разделения доступа по ролям и регионам
- изоляции данных партнеров и корпоративных клиентов
- аудита действий с чувствительными данными
- запрета прямого доступа к данным другого домена без API или событийного контракта

## 6. Подход к аналитике и ML

Для аналитики и ML используется безопасная модель данных:

- персональные данные не передаются в глобальное аналитическое хранилище без необходимости
- для отчетности используются агрегаты
- для ML-моделей используются обезличенные признаки
- доступ к сырым данным ограничен
- события из регионов передаются в аналитическое хранилище только после фильтрации чувствительных данных


## 7. Последствия

### Положительные

- Снижается риск нарушения локальных требований к данным
- Персональные и платежные данные не реплицируются глобально без необходимости
- Поддерживается региональная изоляция данных
- Архитектура согласуется с regional ownership и multi-region deployment
- Упрощается запуск GoFuture в новых странах

### Отрицательные

- Усложняется управление данными между регионами
- Не все данные можно использовать для глобальной аналитики в исходном виде
- Требуется поддерживать разные правила хранения для разных регионов
- Возрастает сложность аудита и контроля доступа
