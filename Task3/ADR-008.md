# ADR-008: Схема репликации данных между регионами GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture разворачивается в нескольких географических регионах для обеспечения низкой задержки и высокой доступности для пользователей в Юго-Восточной Азии и Южной Америке

В ADR-007 выбраны следующие регионы развертывания:

- Singapore
- Jakarta
- Malaysia
- São Paulo
- Santiago

## 2. Требования

Схема репликации должна обеспечивать:

- сохранение работоспособности при отказе региона
- минимизацию потери данных при аварийном переключении
- низкую задержку для runtime-сценариев
- отсутствие конфликтов записи между регионами
- возможность репликации аналитических данных
- учет локальных требований к хранению персональных и платежных данных
- поддержку доменной модели данных и событийной архитектуры

## 3. Решение

Для GoFuture выбирается модель **regional ownership**.

Это означает:
- каждый пользователь, водитель, поездка и платеж имеют основной регион хранения
- запись выполняется только в основном регионе объекта
- в другие регионы данные реплицируются для чтения, аналитики или аварийного восстановления
- при failover резервный регион временно становится владельцем данных
- после восстановления основного региона выполняется сверка и обратная синхронизация

Такой подход позволяет избежать конфликтов записи между регионами и сохранить низкую задержку для пользовательских сценариев.

## 4. Общая схема репликации

Для Юго-Восточной Азии используется active-active модель между регионами Singapore, Jakarta и Malaysia. Каждый регион обслуживает локальных пользователей и является основным регионом записи для данных, созданных в этом регионе. При этом запись по конкретному объекту выполняется только в одном регионе-владельце, чтобы избежать конфликтов

Критичные данные реплицируются в соседние регионы для аварийного восстановления. Singapore и Malaysia используются как взаимные резервные регионы. Jakarta обслуживает индонезийский сегмент и реплицирует критичные данные в Singapore как в ближайший резервный регион

Для Южной Америки используется схема primary-standby. São Paulo является основным регионом для обработки пользовательского трафика, хранения runtime-данных и выполнения операций. Santiago используется как резервный регион для аварийного переключения в случае отказа São Paulo

Аналитические события и данные из регионов передаются в аналитическое хранилище в агрегированном и обезличенном виде

Таким образом, репликация строится по следующим принципам:

- пользовательские runtime-данные записываются в основном регионе пользователя или поездки
- критичные данные асинхронно реплицируются в резервный регион
- быстро меняющиеся данные, например геопозиция водителей, не реплицируются глобально
- аналитика строится на событиях, агрегатах и обезличенных данных
- при отказе региона резервный регион может временно принять его нагрузку

Репликация São Paulo -> Santiago является межоблачной репликацией между AWS и Google Cloud, поэтому требует отдельной сетевой связности, мониторинга и проверки восстановления
## 5. Репликация доменных сервисов

| Сервис               | Репликация                                                                                                                                                                             |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Booking Service      | Заказы и статусы поездок пишутся в регионе создания поездки. Критичные данные асинхронно реплицируются в резервный регион                                                              |
| Driver Service       | Профили водителей реплицируются read-only. Текущие координаты и доступность в основном остаются региональными                                                                          |
| Pricing Service      | Правила и тарифы реплицируются в регионы, где они используются. Расчеты цены сохраняются в регионе поездки                                                                             |
| Payments Service     | Платежные операции хранятся в регионе операции. Критичные данные асинхронно реплицируются в резервный регион. Сохраняются внешние идентификаторы платежей для идемпотентности и сверки |
| Notification Service | Шаблоны и настройки уведомлений реплицируются. История отправки не является критичной для межрегиональной репликации                                                                   |
| Fraud Service        | Правила и результаты проверок могут реплицироваться. Для аналитики передаются события или агрегированные признаки                                                                      |
| Analytics Service    | Получает события и агрегаты из регионов. Персональные данные не должны передаваться без необходимости                                                                                  |

## 6. Репликация событий Kafka

Kafka остается региональной событийной платформой. Каждый регион имеет свой Kafka Cluster

Между регионами реплицируются только необходимые события:

- события для аварийного восстановления
- события для аналитики
- события для антифрод-моделей
- агрегированные события для BI
- технические события для сверки состояния

События активного runtime-сценария не должны без необходимости передаваться между континентами, чтобы не увеличивать задержку

## 7. Согласованность данных

Для большинства доменных данных используется eventual consistency

Это допустимо для:
- аналитики
- уведомлений
- истории поездок
- профилей
- справочников
- антифрод-сигналов

Более строгая согласованность требуется для:
- активной поездки
- статуса заказа
- платежной операции
- назначения водителя

Для таких сценариев используется принцип единственного региона записи: пока объект принадлежит конкретному региону, запись выполняется только там

## 8. Последствия

### Положительные

- Снижается риск конфликтов записи между регионами
- Runtime-сценарии остаются быстрыми, так как запись выполняется локально
- Есть резервные копии критичных данных в соседних регионах
- Можно отдельно масштабировать Юго-Восточную Азию и Южную Америку
- Аналитика может строиться на агрегированных региональных данных

### Отрицательные

- Появляется задержка репликации между регионами
- Усложняется восстановление после failover
- Требуется сверка данных после аварийного переключения
- Не все данные можно свободно реплицировать из-за локальных требований
- Для Южной Америки появляется дополнительная сложность из-за multi-cloud репликации между São Paulo и Santiago
