## Сквозная логика архитектурных решений

1. В ADR-001 фиксируются функциональные и нефункциональные требования.
2. В ADR-002 определяется карта сервисов и доменных границ.
3. В ADR-003 задается очередность выделения сервисов из монолита.
4. В ADR-004 описываются механизмы обратной совместимости.
5. В ADR-005 описывается миграция данных из монолита в доменные сервисы.
6. В ADR-006 проектируется событийная платформа на базе Kafka и Flink.
7. В ADR-007–ADR-011 проектируется multi-region архитектура: выбор регионов, репликация, геомаршрутизация, failover и compliance.
8. В ADR-012 проектируется data platform для BI и ML.
9. В ADR-013 проектируется мультитенантная платформа для партнеров.

## Основные архитектурные решения

- переход от Django-монолита к микросервисной архитектуре;
- декомпозиция по доменам Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud;
- постепенная миграция через Strangler Fig;
- сохранение обратной совместимости API на период миграции;
- разделение данных по доменным сервисам;
- событийная интеграция через Kafka;
- потоковая обработка через Flink;
- аналитическое хранилище ClickHouse;
- BI через DataLens;
- multi-region deployment для Юго-Восточной Азии и Южной Америки;
- regional ownership для данных;
- GeoDNS / Global Traffic Manager для маршрутизации пользователей;
- failover между регионами;
- regional data compliance;
- Data Platform для ML-моделей динамического ценообразования, прогнозирования спроса и антифрода;
- мультитенантность через shared control plane и isolated tenant data plane;
- IAM / SSO / RBAC для управления доступом партнеров.

## Краткий итог

Решение описывает поэтапный переход GoFuture от монолита к целевой архитектуре, которая поддерживает:

- обработку высокой нагрузки;
- независимое развитие доменных сервисов;
- событийное взаимодействие;
- глобальное развертывание в нескольких регионах;
- аварийное переключение;
- локальный compliance;
- аналитику и ML;
- запуск партнеров в мультитенантной модели.
