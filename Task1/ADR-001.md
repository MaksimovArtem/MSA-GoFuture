# ADR-001: Проработка нефункциональных требований для перехода GoFuture к микросервисной архитектуре

**Автор: Максимов Артем**

## 1. Контекст

Платформа «GoFuture» переходит от монолитной архитектуры к микросервисной. Текущая система плохо масштабируется при росте нагрузки, имеет высокий MTTR, подвержена каскадным отказам и замедляет выпуск новых функций

Цель данного ADR - зафиксировать основные функциональные и нефункциональные требования, которые будут учитываться при проектировании целевой архитектуры

## 2. Функциональные требования

| **№** | **Требование**                                                                                                                            |
| :---: | :---------------------------------------------------------------------------------------------------------------------------------------- |
| **F** | **Functionality**                                                                                                                         |
|  F1   | Система должна поддерживать полный жизненный цикл поездки: создание заказа, назначение водителя, изменение статусов, оплату и уведомления |
|  F2   | Система должна поддерживать динамическое ценообразование в режиме near real-time                                                          |
|  F3   | Система должна поддерживать умное распределение водителей с учетом спроса, доступности водителей и предотвращения горячих зон             |
|  F4   | Система должна поддерживать локальные платежные, банковские, картографические и push-интеграции                                           |
|  F5   | Система должна поддерживать работу с пассажирами, водителями, корпоративными клиентами и партнерами                                       |

## 3. Нефункциональные требования

| **№**  | **Требование**                                                                                                                                     |
| :----: | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| **U**  | **Usability**                                                                                                                                      |
|   U1   | Пассажирское приложение должно оставаться быстрым и понятным при основных сценариях: заказ поездки, получение цены, отслеживание водителя и оплата |
|   U2   | Водительское приложение должно своевременно получать новые заказы и обновления статусов поездки                                                    |
|   U3   | Корпоративный портал должен позволять управлять поездками, пользователями и отчетностью без участия поддержки                                      |
|   U4   | API для партнеров должен быть документирован и удобен для интеграции                                                                               |
| **R**  | **Reliability**                                                                                                                                    |
|   R1   | Критичные сервисы должны обеспечивать доступность 99,95%                                                                                           |
|   R2   | MTTR должен быть снижен с более чем 4 часов до менее 1 часа                                                                                        |
|   R3   | Отказ одного сервиса не должен приводить к отказу всей платформы                                                                                   |
|   R4   | Система должна корректно работать при временной недоступности внешних сервисов: платежей, карт, банковских API и push-уведомлений                  |
|   R5   | Платежные операции должны защищаться от повторного списания и неконсистентных состояний                                                            |
|   R6   | Управление идентификацией и доступом должно быть централизованным                                                                                  |
| **P**  | **Performance**                                                                                                                                    |
|   P1   | Система должна поддерживать обработку до 500000 конкурентных поездок                                                                               |
|   P2   | Основные доменные сервисы должны масштабироваться горизонтально                                                                                    |
|   P3   | Система должна поддерживать автоматическое масштабирование в нескольких регионах                                                                   |
|   P4   | Очереди и фоновые обработчики должны масштабироваться в зависимости от нагрузки                                                                    |
|   P5   | Расчет цены и подбор водителя должны выполняться достаточно быстро для сценария заказа поездки в реальном времени                                  |
|   P6   | Время сборки и доставки изменений должно быть сокращено, чтобы поддержать выпуск новых функций до двух недель                                      |
| **S**  | **Supportability**                                                                                                                                 |
|   S1   | Критичные сервисы должны быть покрыты мониторингом, логированием и трейсингом                                                                      |
|   S2   | Для критичных сервисов должны быть настроены метрики, дашборды и алерты                                                                            |
|   S3   | Доменные сервисы должны иметь независимые CI/CD-пайплайны и возможность независимого релиза                                                        |
|   S4   | Для сервисов должны быть определены владельцы и зоны ответственности                                                                               |
|   S5   | Архитектура должна позволять быстрее находить и устранять причины инцидентов                                                                       |
| **+R** | **+ Restrictions**                                                                                                                                 |
|  +R1   | Миграция от Django-монолита к микросервисной архитектуре должна выполняться постепенно                                                             |
|  +R2   | На период миграции должна сохраняться совместимость с существующими мобильными приложениями и API                                                  |
|  +R3   | Целевая архитектура должна поддерживать multi-region deployment минимум в трех регионах                                                            |
|  +R4   | Система должна учитывать локальные регуляторные требования разных стран                                                                            |
|  +R5   | Платформа должна поддерживать мультитенантность для партнеров и регионов                                                                           |
|  +R6   | Необходимо перейти от базового Docker-based deployment к полноценной оркестрации контейнеров                                                       |
|  +R7   | Интеграции с локальными платежными, банковскими, картографическими и push-сервисами должны подключаться без существенных изменений ядра платформы  |
|  +R8   | Архитектура должна поддерживать data-driven решения и ML-модели для прогнозирования спроса, ценообразования и предотвращения фрода                 |

## 4. Последствия

- Система должна быть декомпозирована на независимые доменные сервисы
- Для каждого сервиса должна быть определена зона ответственности и владелец
- Архитектура должна поддерживать горизонтальное масштабирование и multi-region deployment
- Критичные сервисы должны быть устойчивы к сбоям других сервисов и внешних интеграций
- Необходимо перейти к независимым CI/CD-пайплайнам и независимым релизам сервисов
- На время миграции необходимо сохранить совместимость с существующими клиентскими приложениями и API
- Для сервисов должны быть настроены мониторинг, логирование, трейсинг и алерты
- Данные должны постепенно разделяться по доменам, чтобы снизить связанность с общей базой монолита
