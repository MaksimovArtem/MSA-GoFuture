# ADR-007: Выбор регионов развертывания GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture должна обеспечить 99,95% доступности и низкую задержку для пользователей в Юго-Восточной Азии и Южной Америке

## 2. Требования

Регионы развертывания должны обеспечивать:
- низкую задержку для пользователей в Юго-Восточной Азии и Южной Америке
- возможность масштабировать нагрузку по регионам
- возможность изоляции сбоев одного региона от остальных
- поддержку локальных платежных, банковских и картографических интеграций
- возможность учитывать локальные регуляторные требования

## 3. Решение

Для целевого глобального развертывания выбирается AWS как основная облачная платформа

Причины выбора:
- AWS имеет регионы в Юго-Восточной Азии и Южной Америке
- регионы можно выбирать ближе к пользователям для снижения задержки
- платформа подходит для построения multi-region архитектуры
- есть возможность развернуть независимые региональные инсталляции GoFuture
- есть managed-сервисы для балансировки, баз данных, событийной платформы, мониторинга и disaster recovery

Текущая платформа использует Yandex Cloud, однако его регионального покрытия недостаточно для целевого глобального развертывания в Юго-Восточной Азии и Южной Америке

Для резервного региона Южной Америки используется multi-cloud допущение: в качестве резервной площадки выбирается Google Cloud Santiago. Это позволяет оставить резервный регион внутри Южной Америки и не переключать пользователей Южной Америки в Северную Америку

## 3.1. Выбранные регионы

| Регион | Cloud provider | Обозначение региона | Назначение | Обоснование |
|---|---|---|---|---|
| Singapore | AWS | `ap-southeast-1` | Основной регион для Юго-Восточной Азии | Сингапур является крупным сетевым и бизнес-хабом региона. Подходит для обслуживания пользователей из Сингапура, Малайзии, Таиланда, Вьетнама, Филиппин и части Индонезии |
| Jakarta | AWS | `ap-southeast-3` | Локальный регион для Индонезии | Индонезия является крупным рынком Юго-Восточной Азии. Отдельный регион снижает задержку для локальных пользователей и позволяет учитывать требования к локальному хранению данных |
| Malaysia | AWS | `ap-southeast-5` | Дополнительный регион Юго-Восточной Азии | Используется для расширения покрытия, распределения нагрузки и резервирования внутри Юго-Восточной Азии |
| São Paulo | AWS | `sa-east-1` | Основной регион для Южной Америки | Используется как основной регион для пользователей Бразилии и соседних стран Южной Америки |
| Santiago | Google Cloud | `southamerica-west1` | Резервный регион для Южной Америки | Используется как резервный регион для Южной Америки. Позволяет при отказе São Paulo переключать пользователей на регион внутри Южной Америки, а не в Северную Америку |
## 3.2. Обоснование выбора

Основная нагрузка GoFuture ожидается в Юго-Восточной Азии и Южной Америке. Поэтому пользовательские runtime-сервисы должны быть расположены ближе к этим регионам

### 3.2.1 Юго-Восточная Азия

Для Юго-Восточной Азии выбирается несколько регионов: Singapore, Jakarta и Malaysia. Это позволяет снизить задержку для пользователей, распределить нагрузку между странами и избежать зависимости от одного региона. Singapore используется как основной регион, Jakarta — как локальный регион для Индонезии, Malaysia — как дополнительный регион для масштабирования и резервирования

### 3.2.2 Южная Америка

Для Южной Америки выбирается São Paulo как основной регион, а в качестве резервного региона выбирается Santiago. Такой регион позволяет сохранить аварийное переключение внутри Южной Америки и снизить задержку по сравнению с переключением пользователей в Северную Америку. Так как Santiago используется в рамках другого облачного провайдера, это добавляет multi-cloud сложность, но лучше соответствует требованию низкой задержки для пользователей Южной Америки

Таким образом, целевая схема развертывания включает более трех регионов:

- Singapore
- Jakarta
- Malaysia
- São Paulo
- Santiago

Такой выбор позволяет GoFuture снизить задержку для пользователей в целевых регионах, обеспечить географическое распределение нагрузки и подготовить основу для дальнейшей реализации репликации данных, геомаршрутизации и аварийного переключения

## 4. Альтернативы

### 4.1 Оставить только Yandex Cloud

Yandex Cloud не обеспечивает достаточного регионального покрытия для низкой задержки в Юго-Восточной Азии и Южной Америке

### 4.2 Развернуть систему только в одном глобальном регионе

Один регион не сможет обеспечить низкую задержку одновременно для Юго-Восточной Азии и Южной Америки

### 4.3 Использовать только два региона: один для Юго-Восточной Азии и один для Южной Америки

Требование предполагает развертывание более чем в трех географических регионах

### 4.4 Использовать регион Северной Америки как резервный для Южной Америки

Не выбрано, так как такой вариант увеличивает задержку для пользователей Южной Америки при аварийном переключении. Для резервирования южноамериканского сегмента предпочтительнее использовать Santiago как регион внутри Южной Америки

## 5. Последствия

### Положительные

- Снижается задержка для пользователей в Юго-Восточной Азии и Южной Америке
- Архитектура соответствует требованию развертывания более чем в трех регионах
- Появляется основа для регионального масштабирования
- Снижается зависимость от одного региона
- Для Южной Америки появляется резервный регион внутри того же континента
- Упрощается дальнейшая реализация failover и локального compliance
### Отрицательные

- Возрастает инфраструктурная сложность
- Увеличивается стоимость эксплуатации
- Появляется необходимость управлять межрегиональной репликацией данных
- Требуется более сложный мониторинг по регионам
- Нужно учитывать локальные требования к данным и интеграциям
- Использование Santiago как резервного региона добавляет multi-cloud сложность
