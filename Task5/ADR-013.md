# ADR-013: Мультитенантная платформа GoFuture для партнеров

**Автор: Максимов Артем**

## 1. Контекст

GoFuture должна быстро запускать решения для партнеров в новых регионах
Партнеры могут использовать корпоративный портал, партнерские API и отдельные функции платформы

## 2. Требования

Мультитенантная платформа должна обеспечивать:

- изоляцию данных между партнерами
- tenant-aware доступ к API и данным
- IAM-систему с RBAC и SSO
- автоматизированный onboarding нового партнера
- кастомизацию функциональности по tenant
- мониторинг технических и бизнес-метрик по tenant
- аудит действий пользователей, администраторов и сервисов

## 3. Решение

Решение представлено в **Tenants_C4.png**

### 3.1 Разделение по тенантам

Для GoFuture выбирается модель **shared control plane + isolated tenant data plane**.

Это означает:

- у каждого партнера есть уникальный `tenant_id`
- общие управляющие сервисы используются всеми партнерами
- данные каждого партнера хранятся в отдельной tenant database
- доступ к данным всегда выполняется с учетом tenant-контекста
- настройки партнера хранятся в control plane
- кастомизация выполняется через tenant configuration и feature flags
- подключение нового партнера автоматизируется через onboarding-процесс

Для изоляции данных выбирается подход **database-per-tenant**.

Причины выбора:

- сильная изоляция данных между партнерами
- проще выполнять compliance-требования
- проще делать backup, restore и удаление данных конкретного tenant
- ниже риск межтенантной утечки данных

Недостаток подхода — увеличивается количество баз данных и усложняется эксплуатация миграций схем

### 3.2. Onboarding нового партнера

Подключение нового партнера выполняется автоматически:

1. Platform Admin создает заявку на подключение партнера
2. Partner Onboarding Service создает новый tenant
3. Tenant Management Service сохраняет tenant metadata
4. Provisioning Service создает tenant database
5. IAM / SSO создает роли, пользователей и SSO-настройки
6. Feature Flag Service включает нужные функции партнера
7. Observability Stack начинает собирать метрики и логи по tenant
8. Partner Admin получает уведомление о готовности окружения

## 4. Мониторинг мультитенантного окружения

Метрики и логи должны содержать:

- tenant_id
- region_id
- service
- endpoint
- status
- error_type

Основные метрики:

|Категория|Метрики|
|---|---|
|API|latency, error rate, request rate по tenant|
|IAM|успешные и неуспешные логины, ошибки SSO, ошибки авторизации|
|Onboarding|статус подключения tenant, ошибки provisioning, длительность onboarding|
|Data isolation|ошибки tenant context, попытки доступа к чужому tenant|
|Business metrics|поездки, оплаты, отмены, выручка по tenant|

Основные алерты:

- рост 5xx у конкретного tenant
- ошибки SSO у конкретного tenant
- ошибка onboarding
- попытка доступа к данным другого tenant
- превышение лимитов API tenant

## 5. Таблица ролей и уровней доступа

|Роль|Уровень доступа|Что может делать|Ограничения|
|---|---|---|---|
|Platform Admin|Global|Создавать tenant-ов, запускать onboarding, управлять глобальными настройками платформы|Не должен работать с операционными данными tenant без отдельного audit-доступа|
|Tenant Admin|Tenant|Управлять пользователями, ролями, настройками и feature flags своего tenant|Нет доступа к другим tenant|
|Operations Manager|Tenant|Смотреть поездки, водителей и операционные отчеты своего tenant|Нет доступа к платежным настройкам и данным других tenant|
|Finance Manager|Tenant|Смотреть платежи, выплаты и финансовые отчеты своего tenant|Нет доступа к данным других tenant и глобальным настройкам|
|Support|Tenant / restricted|Смотреть данные пользователей и поездок для обработки обращений|Ограниченный доступ, все действия логируются|
|Analyst|Tenant / read-only|Смотреть дашборды и отчеты своего tenant|Только чтение, без доступа к сырым персональным и платежным данным|
|API Client / Service Account|Tenant / API-only|Вызывать партнерские API в рамках своего tenant|Только разрешенные API и только в пределах tenant|
|Partner User|Tenant / limited|Работать с функциями портала согласно назначенной роли|Нет доступа к администрированию tenant|

## 6. Последствия

### Положительные

- Данные партнеров изолированы друг от друга
- Партнеров можно быстрее запускать в новых регионах
- IAM и SSO централизуют управление доступом
- Кастомизация функций выполняется через tenant configuration
- Onboarding становится воспроизводимым и автоматизированным
- Мониторинг позволяет видеть проблемы по конкретному tenant

### Отрицательные

- Возрастает инфраструктурная сложность
- Увеличивается количество tenant databases
- Усложняется сопровождение миграций схем
- Требуется строго контролировать tenant-aware доступ в сервисах
- Нужно следить за стоимостью и ресурсами по каждому tenant
