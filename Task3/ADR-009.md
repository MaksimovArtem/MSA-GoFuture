# ADR-009: Геомаршрутизация пользователей GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture разворачивается в нескольких географических регионах для обеспечения низкой задержки и высокой доступности для пользователей в Юго-Восточной Азии и Южной Америке

В ADR-007 выбраны регионы развертывания: Singapore, Jakarta, Malaysia, São Paulo и Santiago. В ADR-008 определена модель regional ownership, при которой пользовательские данные и runtime-сценарии обрабатываются в основном регионе пользователя или поездки

Для корректной работы такой архитектуры необходимо направлять пользователей в ближайший доступный регион

## 2. Требования

Механизм геомаршрутизации должен обеспечивать:

- направление пользователя в ближайший доступный регион
- учет состояния региона через health checks
- возможность исключить недоступный регион из маршрутизации
- поддержку аварийного переключения на резервный регион
- низкую задержку для пользователей в Юго-Восточной Азии и Южной Америке
- сохранение regional ownership для пользовательских данных

## 3. Решение

Для маршрутизации используется провайдер-независимый Global Traffic Manager / GeoDNS

C4-диаграмма представлена в **GeoRouting_C4.png**

Пользователь обращается к глобальному endpoint GoFuture. Global Traffic Manager определяет подходящий регион на основе географии пользователя, latency и результатов health checks. После этого пользовательский трафик направляется в региональный API Gateway

В каждом регионе развернут свой API Gateway и набор доменных сервисов. API Gateway передает запросы в локальные сервисы региона. Если регион недоступен, он исключается из маршрутизации, а пользователи перенаправляются в резервный регион

## 4. Правила маршрутизации

| Пользовательский сегмент                               | Основной регион | Резервный регион |
| ------------------------------------------------------ | --------------- | ---------------- |
| Юго-Восточная Азия за исключением Индонезии и Малайзии | Singapore       | Malaysia         |
| Индонезия                                              | Jakarta         | Singapore        |
| Малайзия                                               | Malaysia        | Singapore        |
| Южная Америка                                          | São Paulo       | Santiago         |

## 5. Проверка доступности регионов

Global Traffic Manager выполняет health checks региональных API Gateway

Регион считается недоступным, если:

- API Gateway не отвечает
- критичные сервисы региона недоступны
- резко выросла ошибка 5xx
- региональный latency превышает допустимый порог
- регион вручную выведен из обслуживания

После восстановления регион может быть возвращен в маршрутизацию.

## 6. Особенности

Геомаршрутизация направляет пользователя в ближайший доступный регион, но не должна нарушать regional ownership

Если пользовательские данные принадлежат конкретному региону, то запись выполняется в регионе-владельце. При временном переключении в резервный регион он может обрабатывать запросы только в рамках сценария failover

## 7. Альтернативы

### 7.1 Один глобальный endpoint без геомаршрутизации

Не выбрано, так как не обеспечивает низкую задержку для пользователей в разных частях мира

### 7.2 Ручное переключение трафика между регионами

Не выбрано, так как ручное переключение увеличивает время восстановления и не подходит для требования высокой доступности

### 7.3 Маршрутизация только по географии без health checks

Не выбрано, так как пользователь может быть направлен в ближайший, но недоступный регион

## 8. Последствия

### Положительные

- Пользователи направляются в ближайший доступный регион
- Снижается latency для Юго-Восточной Азии и Южной Америки
- Появляется основа для автоматического failover
- Отказ региона не требует ручного изменения клиентских приложений
- Можно независимо выводить регионы из эксплуатации

### Отрицательные

- Требуется поддерживать health checks для регионов
- Усложняется диагностика маршрутизации
- Нужно учитывать regional ownership при переключении пользователя
- Возможны задержки DNS-кеша при изменении маршрута
