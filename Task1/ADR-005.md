# ADR-005: План миграции данных при выделении сервисов GoFuture

**Автор: Максимов Артем**

## 1. Контекст

GoFuture переходит от Django-монолита с общей PostgreSQL БД к микросервисной архитектуре
Согласно ADR-002, каждый доменный сервис должен постепенно получить собственную зону ответственности и модель данных
Миграция должна быть постепенной, безопасной и совместимой с уже существующими мобильными приложениями, корпоративным порталом и внешними API

## 2. Требования

План миграции данных должен учитывать:

- наличие исторических данных
- необходимость продолжать работу системы во время миграции
- сохранение обратной совместимости API
- постепенное выделение сервисов согласно ADR-003
- минимизацию риска потери или дублирования данных
- возможность проверки корректности миграции
- постепенное разделение общей БД монолита на доменные модели данных
- 
Из-за большого объема исторических и операционных данных миграция не должна выполняться единовременно
## 3. Решение

Для миграции данных принимается поэтапный подход(каждый домен является владельцем своих данных):

1. Подготовить схему данных нового сервиса
2. Выполнить первичную загрузку данных из монолита
3. Настроить синхронизацию изменений на переходный период
4. Переключить чтение на новый сервис
5. Переключить запись на новый сервис
6. Остановить синхронизацию и удалить зависимость от таблиц монолита

## 4. Общие механизмы миграции данных

| Механизм                | Описание                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Пакетная миграция       | Исторические данные переносятся небольшими порциями, чтобы не создавать критичную нагрузку на основную БД                     |
| Синхронизация изменений | На переходном этапе изменения из монолита передаются в новый сервис через события, CDC или временные интеграционные механизмы |
| Read switch             | Сначала новый сервис начинает обслуживать чтение данных                                                                       |
| Write switch            | После проверки корректности запись переводится в новый сервис                                                                 |
| Сверка данных           | После миграции сравниваются количество записей, ключевые поля и бизнес-состояния                                              |
| Идемпотентность         | Повторная обработка события или команды не должна приводить к дублированию поездок, платежей или статусов                     |

## 5. План миграции данных по сервисам

Порядок вынесения определен в ADR-003

| Этап | Сервис               | Данные                                                                                             | Подход к миграции                                                                                                                                                |
| ---- | -------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Notification Service | Шаблоны уведомлений, настройки каналов                                                             | Перенести шаблоны и настройки. Новые уведомления отправлять через новый сервис<br>Миграция исторических данных не требуется                                      |
| 2    | Geography Service    | Геозоны, города, регионы, маршруты, настройки картографических интеграций                          | Пакетно перенести справочные геоданные и настройки регионов                                                                                                      |
| 3    | Pricing Service      | Тарифы, правила ценообразования, коэффициенты спроса, история расчетов цены                        | Сначала перенести правила и тарифы. Новый сервис параллельно считает цену; результаты сравниваются с монолитом перед переключением                               |
| 4    | Driver Service       | Профили водителей, статусы, доступность, привязка к регионам, история активности                   | Профили перенести пакетно. Быстро меняющиеся данные, например статусы и доступность водителей, синхронизировать событиями                                        |
| 5    | Payments Service     | Платежи пассажиров, выплаты водителям, статусы транзакций, внешние идентификаторы платежных систем | Сначала перенести историю и справочные данные, затем включить новую обработку платежей. Обязательны сверка с платежными провайдерами и идемпотентность операций  |
| 6    | Booking Service      | Заказы, поездки, статусы поездок, связь пассажира, водителя, цены и платежа                        | Самая сложная миграция. Исторические поездки переносить пакетно или оставить в архивном режиме. Новые поездки после переключения создавать уже в Booking Service |
| 7    | Fraud Service        | Правила фрода, признаки подозрительных операций, результаты проверок                               | Сервис в основном строится на событиях из Booking, Payments и Driver. Исторические данные загрузить из монолита при необходимости                                |
| 8    | Analytics Service    | События поездок, платежей, водителей, ценообразования, фрода                                       | Исторические данные переносить в аналитическое хранилище пакетно. Новые данные получать через события от доменных сервисов                                       |

## 6. Детализация по критичным доменам

### 6.1 Booking Service

Booking Service отвечает за жизненный цикл поездки, поэтому его данные мигрируются после выделения основных зависимых сервисов

Подход:

- исторические поездки мигрировать пакетно
- старые завершенные поездки можно оставить доступными через read-only слой
- новые поездки после переключения создавать в Booking Service
- статусы поездок должны синхронизироваться до полного отключения монолитной логики

### 6.2 Payments Service

Payments Service является критичным из-за риска повторных списаний и неконсистентных состояний

Подход:

- сохранить внешние идентификаторы платежей и выплат
- обеспечить идемпотентность операций
- выполнять сверку с платежными и банковскими системами
- не удалять старые платежные данные из монолита до завершения проверки
- сначала перенести чтение истории платежей, затем обработку новых операций
## 7. Последствия

### Положительные

- Снижается риск потери данных при миграции
- Сервисы постепенно получают собственные модели данных
- Можно переносить данные без остановки бизнеса
- Упрощается дальнейшее независимое развитие сервисов
- Исторические данные не обязательно перетаскивать в runtime-сервисы полностью

### Отрицательные

- На переходном этапе потребуется синхронизация данных между монолитом и новыми сервисами
- Временно возрастает сложность архитектуры
- Потребуется дополнительная проверка корректности миграции
- Возможны временные дубли данных между монолитом и сервисами
