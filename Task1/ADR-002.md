# ADR-002: Формирование карты сервисов и доменных границ GoFuture

**Автор: Максимов Артем**

## 1. Контекст

Платформа GoFuture переходит от монолитной архитектуры к микросервисной. Текущая система использует единую кодовую базу Django и общую PostgreSQL БД, что приводит к проблемам масштабирования, высокому MTTR и длительному time-to-market.

Для обеспечения независимого масштабирования, multi-region deployment и независимой разработки необходимо определить карту сервисов и доменные границы системы.

## 2. Решение

В качестве первичных границ декомпозиции принимаются существующие продуктовые домены компании: Booking, Driver, Pricing, Payments, Notification, Geography, Analytics и Fraud

Такая декомпозиция соответствует организационной структуре GoFuture и позволяет постепенно перейти от Django-монолита к независимым доменным сервисам. Карта сервисов может уточняться по мере миграции, но на первом этапе используется следующая структура:

| Сервис               | Ответственность                                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Booking Service      | Управление жизненным циклом поездки: создание заказа, изменение статусов, завершение поездки и координация сценария поездки |
| Driver Service       | Управление водителями, их статусами, доступностью, подбором и распределением водителей                                      |
| Pricing Service      | Динамическое ценообразование и расчет стоимости поездки                                                                     |
| Payments Service     | Обработка оплат пассажиров, выплат водителям и интеграция с платежными и банковскими сервисами                              |
| Notification Service | Отправка push-уведомлений пассажирам и водителям                                                                            |
| Geography Service    | Работа с геоданными, маршрутами, зонами и картографическими сервисами                                                       |
| Analytics Service    | Сбор событий, аналитика в реальном времени, ML-пайплайны и data-driven сценарии                                             |
| Fraud Service        | Выявление подозрительных операций и предотвращение мошенничества                                                            |

Каждый сервис:

- имеет собственную зону ответственности;
- постепенно получает собственную модель данных;
- разворачивается независимо;
- масштабируется независимо;
- взаимодействует с другими сервисами через API и асинхронные события;
- не должен напрямую изменять данные другого сервиса.
## 3. Последствия

### Положительные

- Поддержка горизонтального масштабирования
- Независимое масштабирование сервисов
- Независимая разработка и поставка функциональности
- Снижение связанности компонентов системы

### Отрицательные

- Усложнение межсервисного взаимодействия, необходимость управлять распределенными данными
- Необходимость версионировать API и события между сервисами
- Рост требований к мониторингу и observability
- Усложнение эксплуатации системы
